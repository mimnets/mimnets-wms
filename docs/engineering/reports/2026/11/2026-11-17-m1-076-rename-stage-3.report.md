## Implicit state review

1. **Stored names vs registered names.** This is the state the stage adds:
   - It moves once, forward, at the first start of the new code. Core runs the migration before
     `ready`, under the migration lock, and records it in `aposMigrations`.
   - Restoring an older backup returns the database to the old names without the record. The same
     migration runs at the next start (tested by the second run).
   - Old code on migrated data is not supported. Rollback is a restore (§12.5), and the runbook says
     so.
2. **Saved versions** were a second copy of this state. Without the rewrite, "restore version" would
   have brought back old names. They are now migrated with the docs.
3. **Scoped names** are a third copy: core sets them only on save but reads them on every load.
   They are migrated.
4. **Transient state** resets once at the release; listed in the runbook:
   - form fill tokens in open pages;
   - the rate-limit and duplicate-submission cache namespaces;
   - the admin UI in open tabs.
5. **Decision for agents:** the AGENTS.md rule now says that renaming a module that stores a type
   ships a migration. The INDEX name map says what is done and what is open.

## Rollback guidance

- Before the release: revert the branch.
- After the release on OCI: staging runbook §12.5. Restore the database to the base backup that
  `deploy.sh` took, then `deploy.sh <previous tag> --rollback`.
- Local: the pre-migration local database was copied into the session scratchpad. That copy is
  not kept after the session. To go back, use any backup from before m1-076; the new code
  migrates it again at the next start.
